# 全司房源价格管理核对工作台 · V2

主入口：https://heifengzhaimogu-wq.github.io/-/price-desk/

角色演示：https://heifengzhaimogu-wq.github.io/-/price-desk/?demo=1

## 身份与范围

| 身份 | 进度范围 | 价格权限 | 执行权限 |
| --- | --- | --- | --- |
| 全司推进负责人 | 全司 → 门店 → 小组 → 个人 → 房源状态 | 无 | 下发任务、配置员工身份、生成激活入口 |
| 门店 BP | 本店 → 小组 → 个人 → 房源状态 | 无 | 跟进进度 |
| 店总 | 本店 → 小组 → 个人 → 房源状态 | 无 | 跟进进度 |
| 店经理 | 本组 → 个人 → 房源状态 | 本组 | 跟进进度与调价明细 |
| 顾问 | 本人房源 | 本人房源 | 核对、提交调价、确认调整完成 |

支持多位全司推进负责人。账号独立，权限由员工档案配置，不能在登录页自行选择身份。演示身份切换只操作虚构数据。

## 首次登录

工号 0321 已配置为首位全司推进负责人。需使用单独交付的专属激活入口设置至少 12 位工作台密码，之后使用“工号后四位或完整工号＋工作台密码”登录。不使用个人邮箱密码。

激活令牌随机生成，服务端只存哈希，7 天有效且单次使用。员工后四位不作为密码；若后四位重复，登录要求完整工号。请尽量在员工档案和导入文件中提供完整工号，文本格式保留前导零。

## 执行流程

推进负责人下载任务模板，填入房源编号、店面、小组、顾问姓名、顾问工号、楼盘、房间号、报价、底价。上传后自动校验并生成店、组、个人任务，已有顾问档案须与导入店组一致；未登记顾问会自动建档，账号激活入口由负责人在成员页生成。一次最多 5000 条、10MB。

每次下发为独立核对批次，默认显示最新批次，也可筛选历史批次或全部批次。顾问可选择价格无误，或填写目标价格及原因，提交后进入“已核对、待完成调价”。顾问在原业务系统实际完成修改后勾选确认，再标记调价已完成。

本工具尚未连接原业务系统，不会自动修改外部房源价格。“调整完成”是顾问确认状态，不是外部接口回执。

核对完成率 = 已核对任务数 / 全部任务数。调价完成率 = 已完成调整任务数 / 需调整任务数。无需调价不计入调价分母；没有需调整任务时显示横线，不显示 100%。相同房源跨批次分别计为不同核对任务。

店经理及顾问可查看核对前价格和目标价格，原始价格快照保留。总负责人、BP 和店总的价格查询被数据库拒绝，前端也不会请求价格表；其导出文件只包含进度与状态。各角色导出当前筛选全部页，范围与数据库权限一致。

## 技术与验收

V2 前端入口为 source/src/workbench.js；src/app.js 等为上一版保留源码，不再参与发布构建。数据库使用独立 desk_* 表，上一版数据没有删除。恢复 V2 时按顺序应用 database-workflow.sql、database-staff-upgrade.sql、database-workflow-baseline.sql、database-staff-collision.sql。正式系统未导入演示房源。

Edge Functions desk-staff-login 和 desk-activate-account 分别用工号＋密码、工号＋单次激活令牌完成认证。Supabase 的内部 Auth 标识由系统生成，不使用员工个人邮箱作为登录标识。服务端管理密钥只在 Edge Functions 中使用，未进入前端或仓库。

已验证五角色数据库范围、三类管理者的价格隔离、顾问本人操作、并发版本保护、前端角色入口、店组个人逐层查看、无价格导出、手机布局，以及隔离测试账号的真实激活和后四位登录。验收测试账号已删除。真实房源尚待导入；真实员工的业务系统改价仍需业务确认。

当前测试：tests/workflow.test.js、tests/workflow-security.sql、tests/workflow-browser.cjs。其他 tests 文件是上一版本的保留验收用例。npm ci 后 npm run build 生成 dist，继续发布到原 price-desk 目录，主链接保持不变。后续源代码更新须更新 index.html 中静态资源版本标记。

## 三个业务模块

主导航现为日常推动、周月复盘、数据管理。成员与权限收纳在数据管理下，房源任务详情属于日常推动的下钻视图。登录页继续采用工号与工作台密码，全部正式数据登录后按既有五角色权限读取。

业务流：导入校验 → 按门店 / 小组 / 顾问工号分配 → 生成需整改任务 → 顾问核对与调整 → 状态回写 → 日常进度及周月复盘共用这些状态。

错误房源清单会把全部导入房源标记为需整改；全量清单按“是否需调整”“错误类型”来源标记识别已知错误，其他房源由顾问核对后判定。尚未配置自动比价规则，不会凭空判断某个价格是否正确。模板的报价、底价必须为有效数字，缺失责任人、重复编号、格式错误等会阻止整批下发。导入前可核对各店组及顾问的分配量，负责人界面不展示价格。

已知需整改房源即使还没核对，也计入整改分母。已知错误不能直接点击“无需调整”消除任务。顾问提交并确认整改完成后，所有层级的同批次进度同步更新；价格仍仅店经理与本人顾问可见。

周度与月度复盘按上海时区识别该期间下发的批次，展示这些任务截至当前的状态，不把当前状态冒充历史期末快照。提供目标完成率、目标套数、实际完成率、门店对比和依据待核对/待整改数量生成的推进重点，不输出未经证实的原因分析。没有目标时显示未设置，没有需整改任务时完成率显示横线。

目标由推进负责人在数据管理中设置。全司完成率目标可作为门店参考，套数目标只适用于对应范围，不重复分配到各店/各组。BP、店总等只能读取授权范围内的目标，不能修改目标。复盘下钻到日常推动时保留期间对应的批次范围。

新升级脚本 database-modules.sql 在既有 V2 脚本之后应用。新增测试为 tests/modules.test.js、tests/modules-security.sql、tests/modules-browser.cjs。正式目标和房源依旧等待业务数据导入，示例目标只存在演示环境。
